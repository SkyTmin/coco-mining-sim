# Ф3-03. Сколько работ и кадров проверил snap

На восьми картинах обычная команда приняла каждую из 24 заведомо неполных запросов. Проверка состава запроса отклонила все 24 до вызова рендера. Во всех восьми корректных запросах по `idle` сохранились содержание и итог сверки: 576 кадров. Эталонная исходная версия `d6ebb31`, Node v24.22.3, один CPU 0 в облачной Linux-машине. [Предрегистрация](protocol.md) · [32 настоящих вызова и результаты опыта](results/coverage.json)

| Запрос, один вызов на картину | Успехов штатной команды, сообщено кадров суммарно | Успехов кандидата, вызвано вычислений клипа |
| --- | ---: | ---: |
| Только существующий `idle` | 8/8, 576 | 8/8, 8 |
| Только неизвестное `idlee` | 8/8, 0 | 0/8, 0 |
| `idle idlee` | 8/8, 576 | 0/8, 0 |
| Один явный пустой строковый аргумент | 8/8, 0 | 0/8, 0 |

`idlee` и пустая строка дали штатное «0 frames identical», смешанная форма посчитала только известное `idle`. Во всех восьми корректных случаях запущен штатный `hashCreature` с отдельным worker, его фактические массивы хешей сопоставлены с golden через `compareGolden`. Счётчик невалидного пути стоит перед вызовом того же вычислителя. Метаданные и исходные модули к этому моменту уже прочитаны; стоимость этой подготовки учитывается ниже. [Путь кандидата](https://github.com/SkyTmin/coco-mining-sim/blob/chatgpt/b25-experiments/docs/research/b23/experiments/03-coverage/src/coverage.mjs) · [Драйвер наблюдений](https://github.com/SkyTmin/coco-mining-sim/blob/chatgpt/b25-experiments/docs/research/b23/experiments/03-coverage/src/observe.mjs)

## Какие старые вызовы сохраняются

В команде `snap <id> --check` отсутствие фильтра по клипам сохраняет значение «все клипы этой работы». Для восьми исходных картин независимо считаны длительности источника с множителем циклов `life` и длины массивов golden: обе стороны дают 240 именованных пар и 45 726 кадров. Это проверка деклараций. Физический полный пересчёт каждого кадра выполняется в отдельной серии Ф0. Повтор одного имени `idle idle` даёт то же множество из одного клипа; порядок результатов при полном покрытии допустимо менять. Новый или удалённый клип и изменение длины возвращают отдельные сообщения о различии. Идентичное число кадров при других пикселях проверяет прежний `compareGolden`. [Ф0](../../baseline.md) · [Объявленные имена и длины](results/coverage.json)

В отдельном принятом `pocket_magnet` `cced294` декларация даёт 26 клипов и 4083 кадров. Исходная версия того же героя дала 4079. На новой версии `idle` тоже совпал. Все три невалидные формы отклонены до расчёта изображений. [Отдельная серия](results/pocket-accepted.json) · [Два полных snap](../../pocket-revision.md)

Дополнительный контроль прежней формы `all` проведён после основного опыта. По 42 исходным ID штатное исключение `experimental` оставляет 41 картину и пропускает только `pocket_magnet_fx`. На `d6ebb31` кандидат сверил декларации 1 139 пар и 164 971 кадра; на `cced294` — те же 1 139 пар и 164 975 кадров. Во второй версии общий счёт увеличился только вслед за обновлением принятого Полюсика. Расчёт RGBA здесь не вызывался; данные — о совместимости отбора и длительностей, а не полный рендер всех 41. Холодные чтения с импортами 4,24 и 4,56 с в разовых прогонах. ## Границы множества работ

- Выделенной штатной функции `snapCommand` передали пустой список картин при `all --check` — код 0, журнал содержит `0/0 identical in 0 s with 0 jobs`. Это проверка диспетчера на искусственно пустом каталоге.
- При одной существующей и одной выдуманной работе обычная команда завершилась с кодом 1. До диагностики второго ID существующий `idle` уже попал в расчёт. Кандидат перечислил неизвестный ID и не вызвал вычислитель.
- У пары действительных работ указали клип, который есть лишь у одной. Штатная команда вернула 0, для одной работы сообщила 0 кадров. Кандидат потребовал присутствия явно запрошенного клипа у каждой выбранной работы. Такая семантика должна быть видна пользователю. Осмысленное выборочное сравнение можно задать отдельными явными списками для разных работ. [Три исхода штатных границ](results/native-boundaries.json) · [Вызовы штатного диспетчера](https://github.com/SkyTmin/coco-mining-sim/blob/chatgpt/b25-experiments/docs/research/b23/experiments/03-coverage/src/boundary.mjs)

На этапе завершения искусственно убирали результат одной пары, укорачивали его, дублировали и меняли 5/9 на 9/5 при той же общей сумме. Все эти варианты распознаны. Независимая ошибка содержимого остаётся за существующим сравнением хешей. Подставные нештатные события не означают, что текущий worker действительно присылал неполные данные. ## Возражение скептика и исправление

У первого кандидата защита «пустой результат» применялась один раз ко всему плану. Независимый скептик подставил две работы: у первой есть `idle`, у второй нет клипов ни в живом описании, ни в эталоне. Исходная реализация вернула успех, позвала вычислитель для первой работы и потеряла вторую. Это отдельный отрицательный результат опыта. Условие перенесено внутрь цикла по ID. Та же пара теперь возвращает `empty-clip-set` для второй работы и ноль вызовов расчёта. Порядок ID и повтор одного из них проблему больше не маскируют. Первичные восемь и принятый Полюсик повторно проверены на окончательной версии. [Исходное возражение](results/reviewer-fixtures-before.json) · [Те же входы после правки](results/reviewer-fixtures-after.json) · [Проба скептика](https://github.com/SkyTmin/coco-mining-sim/blob/chatgpt/b25-experiments/docs/research/b23/experiments/03-coverage/src/reviewer-fixtures.mjs)

## Цена

Холодное чтение описаний, подключение рендера и чтение восьми golden в одном процессе заняли 1,230 с. Штатный CLI для одного действительного `idle`, включая запуск Node и worker, занял 2,954…15,681 с (медиана 7,141 с по восьми разным работам). Это разные границы операции. Экономию времени валидного пути из этих чисел не выводим. В реальном процессе студии уже загруженные описания следует учитывать отдельно от нового чтения всех файлов. Перенос бюджета на другую машину требует нового замера. [Точные времена](results/coverage.json)

По уже подготовленному индексу измерены 31 серия по 100 вычислений запроса после одной прогревающей серии. Каждая точка — среднее время на один вызов в серии. 95-й процентиль взят по 31 такому среднему. Часы wall-time, в машине одновременно работал Ф0 на другом CPU. Выигрыш всей системы и пиковая память нового пути из этого теста не следуют.

## Что переносится в проект Ф4

| Что известно | Как это трактуем | Уверенность и граница |
| --- | --- | --- |
| У валидных `idle` сохранилось совпадение штатных хешей у 8/8, у трёх невалидных форм штатный путь возвращал успех в 24/24. | Проверка заданных ID/имён до рендера предотвращает этот класс ложных подтверждений в опыте. | Высокая в воспроизведённых случаях. Полная совместимость с остальными командами и старыми интеграциями не проверялась. |
| Пробел в результате с сохранённым общим числом пойман по `(id, клип, длина)`. | В итоговом объекте иметь числитель отдельно для каждой запрошенной пары. | Высокая для подставных случаев. Семантическую ошибку в кадре по длине не обнаружить. |
| Построение индекса с нуля и поиск по готовым метаданным имеют разную цену. | Перед выбором реализации найти место, где те же описания уже загружены. | Средняя. Прототип не встроен в боевой CLI; полный бюджет и стоимость других операций требуют отдельной проверки. |

Для повтора задать `D` абсолютным путём к каталогу этого опыта, `T` — временным каталогом. Из `tools/creatures` отдельного checkout указанной версии, с обычными npm-зависимостями. В первом checkout работают первая и вторая команды, в checkout `cced294` — третья.

```sh
taskset -c 0 node --import tsx "$D/src/observe.mjs" "$T"
taskset -c 0 node --import tsx "$D/src/boundary.mjs" "$T"
taskset -c 0 node --import tsx "$D/src/observe.mjs" "$T" pocket
# Для каждой версии из её tools/creatures, с отдельным именем результата.
taskset -c 0 node --import tsx "$D/src/whole-corpus.mjs" "$T/corpus.json"
```
