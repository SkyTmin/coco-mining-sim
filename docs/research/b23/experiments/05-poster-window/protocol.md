# Ф3 · загрузка обложек в пределах экрана

Гипотеза: если создавать растровые поверхности обложек только около видимого участка списка, число пикселей, выделенных под обложки стены, будет ограничено числом видимых работ при росте каталога. Проверка относится к интерфейсу доставки нынешнего пиксель-арта. Художественное правило для самой картины дано владельцем в 957f878c.

До расчёта задаём восемь принятых ID Ф0, размеры 8/41/100/300, ширину окна 390, высоту 844, DPR 2, одну и ту же распакованную текстуру и 5 последовательных положений прокрутки, включая возврат. Две реализации в изолированной странице опыта получают одинаковые координаты нарезки и одинаковое изображение. Первая сохраняет все отдельные холсты, вторая оставляет холсты строк, которые пересекают экран с запасом в одну строку. На каждом положении считаем холсты и их логический объём RGBA. Для всех видимых работ должны совпасть ID и SHA-256 полного RGBA. Ошибка после возврата и потерянный последний предмет отвергают гипотезу так же, как расхождение цветов.

HTTP-доставка отдельных файлов, освобождение нативной памяти, частота кадров на телефоне и синхронность состояния мира не измеряются. Большой общий лист постеров остаётся общей памятью для обоих способов. Восемь исходных ID показывают влияние их разных размеров, расширенные каталоги до 300 повторяют 41 принятую работу. Сравнить с расходом полной галереи в Ф0б. Отдельно записать дополнительное число повторных рисований при прокрутке туда и обратно и задержки кадров на стенде. Это инженерный кандидат на пилот после приёмки проекта, не замена галереи.

До первого запуска планка для 100/300 — не больше 20 выделенных холстов на любой из пяти позиций и одинаковый SHA каждого видимого элемента. Восемь работ полностью помещаются по высоте и служат отрицательным контролем экономии. Не вводим проходного числа миллисекунд на одном настольном Chromium.
